# Deployment

Supabase (database and auth), Render (Go API), Vercel (frontend, later).

## 1. Supabase

1. Create a project. Note the project URL (`https://<ref>.supabase.co`).
2. Database connection strings (Project Settings, Database):
   - **Transaction pooler** (port 6543) for `DATABASE_URL`. The API uses pgx with no named prepared statements, which is what the transaction pooler needs.
   - **Direct connection** (port 5432) for `MIGRATION_DATABASE_URL`. Migrations take advisory locks, which the transaction pooler does not support.
3. Auth: enable the providers you want. The API verifies tokens through `{SUPABASE_URL}/auth/v1/.well-known/jwks.json`, so nothing needs to be copied for projects using asymmetric signing keys. Only for legacy HS256 projects set `SUPABASE_JWT_SECRET`.
4. Never expose the service-role key to the frontend (the backend does not use it at all). The frontend only needs the project URL and the anon key.

## 2. Render (API)

1. Push the repo to GitHub, commit `backend/go.sum` and `backend/internal/db/` (generated by sqlc).
2. In Render choose New, Blueprint, and select the repo. `render.yaml` defines a Docker web service with `/healthz` as health check.
3. Fill in the secrets Render asks for (`sync: false` values):

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Supabase transaction pooler URL |
| `MIGRATION_DATABASE_URL` | Supabase direct URL |
| `SUPABASE_URL` | `https://<ref>.supabase.co` |
| `ALLOWED_ORIGINS` | exact frontend origin, e.g. `https://your-app.vercel.app` (no wildcard) |
| `FRONTEND_URL` | same origin; used for the Gmail callback redirect |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | from Google Cloud (optional) |
| `GOOGLE_REDIRECT_URL` | `https://<render-host>/oauth/gmail/callback` |
| `TOKEN_ENCRYPTION_KEY` | `openssl rand -base64 32`; losing it makes stored Gmail tokens unreadable (users reconnect) |

`AUTO_MIGRATE=true` applies pending migrations at start. Leave `SUPABASE_JWT_SECRET` unset when using asymmetric keys.

4. Verify: `GET https://<render-host>/healthz` returns `{"status":"ok"}`, `/readyz` returns `ready`, and `GET /api/v1/me` with a real Supabase access token returns your user.

Notes: the free Render plan sleeps when idle, so the first request after a pause is slow. Rate limits are per instance and in memory, which is correct for the single instance this app runs.

## 3. Vercel (frontend, when it exists)

Environment variables: `VITE_API_URL` (the Render URL), `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. The frontend sends `Authorization: Bearer <supabase access token>` to the API. After deployment, put its exact origin into `ALLOWED_ORIGINS` and `FRONTEND_URL` on Render.

## Local development against Docker Postgres

See the README: `docker compose up -d`, `go run ./cmd/migrate up`, `go run ./cmd/api`, and `go run ./cmd/devtoken` for tokens (disabled when `APP_ENV=production`).

## Operations

- Migrations: `go run ./cmd/migrate up|down|version` (`down` rolls back one step). Every schema change is a new numbered migration; never edit an applied one.
- Logs are JSON in production with a request id on every line; tokens, query strings and message contents are never logged.
- Graceful shutdown: SIGTERM stops accepting requests and drains for up to 15 seconds.
- Backups: use Supabase's backups. `TOKEN_ENCRYPTION_KEY` is not in the database, so back it up in your secret manager.
